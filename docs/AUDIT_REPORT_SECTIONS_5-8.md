## 5. Problems Discovered & Vulnerability Analysis

Inventory of everything found in the AI-generated output. Items are labelled **Fixed**, **Accepted** (known limitation, deliberately not changed) or **Process** (tooling, not contract logic). No high or medium Slither findings were reported; the Slither output is informational only (see §6).

|---|---|---|---|

| P3 | Low (RPC-only) | Accepted | `currentOfferee` view is O(n²) |

### P1 — Duplicate `NameRegistered` identifier (spec defect copied into code)

1. **Why the AI made the mistake:** the interface table in `SPEC.md` §4 lists the revert `NameRegistered` (startAuction) and the event `NameRegistered(nameHash, domain, owner, id, price)` (payWinningBid). The AI implemented the spec literally and did not check that custom errors and events share one identifier namespace in Solidity. The root cause is in the spec the AI was given, which was not compiled before being finalised.
2. **Why it is problematic:** the contract does not compile (`TypeError: Expression has to be an event invocation`), so nothing can be deployed. Had the AI "fixed" it by silently dropping one of the two, the frontend's error decoding or event indexing would diverge from the spec.
3. **How it was fixed:** the error was renamed `NameTaken`; the event keeps the spec name. Acceptance criterion 5 now expects `NameTaken`. `SPEC.md` was updated to match (§4 table, criterion 5).
4. **Evidence:** test "5. reverts NameTaken when registered" passes; `npx hardhat compile` succeeds (see `hardhat-test-output.txt`).

### P2 — Unbounded rank scan in `payWinningBid`

1. **Why:** `SPEC.md` (R11) chose "no cap on commits, rank by scan" and the AI implemented exactly that. It did not propose a bounded or incrementally maintained ranking because the spec had already accepted the trade-off.
2. **Why it is problematic:** gas grows linearly with the number of eligible bidders. If the count ever grows large enough, the winning bidder cannot pay inside a block, the name stays unregistered, and every bidder in the cascade is blocked in the same way.
3. **How it was handled:** measured rather than fixed. Worst case (lowest-ranked bidder pays last):

   | eligible bids n | `payWinningBid` gas |
   |---|---|
   | 10 | 279,180 |
   | 50 | 473,980 |
   | 200 | 1,204,480 |
   | 600 | 3,152,480 |

   That is about 4,870 gas per additional eligible bid, so a 30M-gas block is reached at roughly 6,000 eligible bidders. Each such bidder must also have locked a 0.005 ETH deposit, so reaching that size is costly for an attacker (about 30 ETH of deposits) but not impossible. **Not fixed.** Options if this needs closing: cap commits per auction (the earlier R5 cap of 20), or maintain a sorted structure at reveal time.
4. **Evidence:** `test/gas.test.ts` output in `hardhat-test-output.txt`.

### P3 — `currentOfferee` is O(n²)

1. **Why:** the AI computed "who has rank k" by computing the rank of each bidder, which is a nested scan.
2. **Why it is problematic:** this is a view used by the frontend over RPC. For large n it can exceed the RPC node's `eth_call` gas cap and make the UI unable to show whose turn it is, although `payWinningBid` itself still works.
3. **How it was handled:** documented in a `@dev` comment on the function. Not fixed. Not measured separately.
4. **Evidence:** none beyond code inspection (flagged by Slither only as `incorrect-equality`, informational).

### P4 — Griefing paths (already in the spec's threat model)

- A bidder with a high eligible bid who never pays delays settlement by one window `S` and forfeits their deposit.
- A front-runner who copies someone's commitment makes the victim's commit revert (`CommitmentUsed`); the victim recommits with a fresh salt. The copier cannot reveal.

Both were listed as accepted in `SPEC.md` §6. Test 14 demonstrates the second one. They are recorded here for completeness; the AI did not introduce them.

### P5 / P6 — Tooling and test-authoring issues

- **P5:** `hardhat compile` crashed (`Cannot read properties of undefined (reading 'fileExists')` in `ts-node`) with the TypeScript version npm resolved. Fixed by pinning `typescript@5.6`. The default npm cache also had a permissions error (`EACCES`); a scratch cache directory was used.
- **P6:** the first test run failed 48/48 because the AI imported `expect` from `hardhat` instead of `chai`. The first gas run failed at n=200 because 200 auto-mined blocks at 1 s each exceeded the 180 s commit window; the test was changed to use long commit and reveal durations.

### P7–P9 — Frontend build issues

- **P7:** the AI typed a "known" expected commitment hash into `frontend/src/lib/domain.test.ts` without computing it; the test failed. The value was replaced with the computed one and relabelled as a regression pin. Real equivalence with the contract is proven by `test/frontend-commitment.test.ts` (a reveal only succeeds if the frontend-built hash matches), which passes. Lesson: an AI-supplied "expected value" must be computed or taken from an independent source, never recalled.
- **P8:** importing the frontend's TypeScript helpers from Hardhat's CommonJS test runner failed with `ERR_REQUIRE_ESM`. Fixed by removing `"type": "module"` from `frontend/package.json` and renaming the Vite config to `vite.config.mts`.
- **P9:** the first screenshot of the dev server showed a different app, because another project's server already held port 5173. That server was left running and the check was repeated on port 5199.

### P10 — "Already committed" shown to everyone (found in manual browser testing)

1. **Why the AI made the mistake:** it reused a shared `ZERO` constant (the 20-byte zero *address*) to test whether `getBid().commitment` (a 32-byte value) was empty. Both are "zero" in the AI's mental model, but the strings differ in length, so the comparison was never true. TypeScript cannot catch this because both are plain strings.
2. **Why it is problematic:** every connected account saw "You have already committed a bid", so nobody could commit through the UI, and the Reveal form's "no commitment" check could never fire. The contract stayed correct, so no funds were at risk, but the main user flow was blocked.
3. **How it was fixed:** added `hasCommitment()` in `frontend/src/lib/domain.ts`, which compares with ethers' `ZeroHash`, and used it in both places in `Auction.tsx`. Added a unit test.
4. **Evidence:** Vitest "hasCommitment" test passes (14/14). The original bug was reported by the user during their first browser run of the commit screen; re-running that screen after the fix has not been recorded yet.

**How it slipped through:** the frontend had no automated tests for the page components, and the headless screenshot only covered demo mode, where this code path is skipped (`me` is null).

### P11 — Stale chain clock on the local node (found in manual browser testing)

1. **Why the AI made the mistake:** the AI treated a local Hardhat node like a live network. It did not consider that automine only creates blocks (and advances `block.timestamp`) when a transaction arrives, and wrote the UI to trust `phaseOf()` as read from the latest block.
2. **Why it is problematic:** on the local node the contract's time lags real time. The UI said "Commit phase" while the real window had passed; the user's commit transaction was then mined at real time and reverted `NotInCommitPhase`. With 30 s phases this made the flow nearly impossible to complete by hand. It does not affect live networks, which produce blocks continuously.
3. **How it was fixed:** `npm run node` now sets `LOCAL_INTERVAL_MINING=1`, which makes Hardhat mine a block every second. The default test run leaves it unset, so tests keep full control of time. The README now recommends at least 120 s phases for manual runs.
4. **Evidence:** a temporary node started with the setting advanced from block 4 to block 7 in 3 s and its latest block timestamp matched wall-clock time (difference 0 s). All 53 Hardhat tests still pass. A complete manual run on the fixed setup has not been recorded yet.

### P12 — "My domains" empty after winning (found in manual browser testing)

1. **Why the AI made the mistake:** `NameRegistered(bytes32 indexed nameHash, string domain, address indexed owner, uint256 indexed id, uint256 price)` has a non-indexed `string domain` between indexed fields. ethers v6 matches filter arguments by *parameter position* (non-indexed ones must be `null`), but the AI assumed the arguments follow only the indexed parameters, and wrote `filters.NameRegistered(null, owner)`. The other six filters happened to have all their indexed fields first, so the assumption held for them.
2. **Why it is problematic:** the query threw `cannot filter non-indexed parameters; must be null`. The hook's error was stored but never shown, so My domains and the dashboard silently listed nothing even though the user owned the name on-chain (`namesOf` returned `['alice']`). A user would think the registration had failed.
3. **How it was fixed:** the filters moved into `frontend/src/lib/filters.ts` (owner now passed as `NameRegistered(null, null, owner)`); My domains, Dashboard and History now show an error line when a load fails instead of staying silently empty. New test `test/frontend-filters.test.ts` runs every filter the UI uses against a real contract after a full auction and checks the returned events for two different users.
4. **Evidence:** the broken call reproduced the exact ethers error against the user's local chain (before the fix); after the fix `npx hardhat test` shows 54 passing, including "every filter the UI uses can be queried, and returns the user's events". A browser re-check has not been recorded yet.

### Checks that found nothing

Reviewed or tested with no defect found: reentrancy on both ETH-sending functions (test 43 uses a malicious receiver); access control (no admin role exists; `setPrimaryName` ownership, bidder-keyed reveal and withdraw); integer issues (Solidity 0.8 checked arithmetic, `bid - deposit` is safe because eligibility requires `bid >= minBid >= deposit`); forced ETH (accounting never reads `address(this).balance`); ETH accounting invariant `balance == treasuryBalance + held deposits`, checked after most state-changing tests.

## 7. Improvements & Refinements

Changes made beyond a literal reading of the spec:

1. **Error rename (`NameTaken`)** to resolve the identifier clash (P1).
2. **`getAuction` returns a named struct (`AuctionView`)** instead of a 12-value tuple. The ABI is equivalent to the spec's tuple, but this avoids "stack too deep" and is easier to consume.
3. **Winner commit index stored (`winnerCommitIndex`)** so `canWithdraw` is O(1) for "ranked below the winner", as the spec's recommendation 6 requires.
4. **Test-only additions:** the reentrancy attacker contract, the accounting invariant helper, the 100-commit test, and the gas scaling measurements.
5. **Slither run and archived output** (not asked for in the spec).

Not done, but identified as worthwhile follow-ups: bound the rank scan or keep a sorted structure (P2); add Foundry fuzz/invariant tests; run on Sepolia; build the frontend.

## 8. Lessons Learned

Based only on this one session:

**Where the AI did well**
- With a precise spec (exact function names, error names, boundary conditions, acceptance criteria) the contract compiled after one rename and 48/48 spec-derived tests passed on the first real run. Specification quality mattered more than prompting skill.
- The AI was fast at the mechanical parts: the O(1) withdrawal check, the phase derivation order, the half-open boundary tests.

**Where it fell short**
- It copied a spec defect (P1) rather than noticing it. It also did not question the unbounded loop (P2) until asked to produce audit evidence; it follows an accepted spec decision rather than challenging it.
- Several first attempts failed for avoidable tooling reasons (P5, P6): wrong import, version mismatch, a timing assumption. None were logic bugs, but they cost iterations.
- Self-authored tests give weaker assurance than independent ones (§6).

**Recommendations for future AI-driven dApp work**
1. Compile the spec's interface before freezing it: a stub contract with just the error, event and function declarations would have caught P1 in seconds.
2. Ask the AI to write a gas-scaling test for every loop over user-controlled data as part of the first pass, not as an afterthought.
3. Keep test authorship partly independent: have a second tool (Slither, Foundry fuzzing) or a human reviewer challenge the AI's tests.
4. Pin toolchain versions (Hardhat, TypeScript, Solidity) in the first prompt.
5. Record real evidence as you go (test logs, tool output), so the report sections are written from facts rather than reconstructed afterwards.
